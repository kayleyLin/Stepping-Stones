# 铺路石志愿者调配助手

两种用法，共用同一套算法：

- **`index.html`** — 双击就能用的单文件网页。录入数据、点计算、拿方案。给排班的人用。
- **Python 版** — 命令行跑，产出 Excel。给需要批处理或接入其他系统时用。

---

## 一、网页版（推荐）

双击 `index.html` 即可，不用装任何东西。界面分五步：

1. **录入数据** — 三种方式任选：上传原始 Excel（自动识别 `vol info` / `site info` 两张表，合并单元格会向下填充）、从 Excel 复制一片区域直接粘贴进表格、手工逐行填。志愿者除了最近地铁站外，若还有其他就近地铁站，或最近站点可换乘的其他地铁线路，也可以一并写明作为候选起点。也可以点「载入 25 Spring 示例」先看效果。
2. **规则参数** — 每人最多带班数、单程舒适阈值、超时惩罚等，默认值来自需求沟通记录。
3. **人工锁定** — 已经想好去哪的老志愿者先钉死，模型只排剩下的人。
4. **通勤时间来源** — 本地估算或高德地图，见下节。
5. **计算** — 结果分六个页签：分配方案、未填补名额、未安置志愿者、时段供需、回填格式、数据告警。可导出 CSV，也可一键复制回填列直接粘回 Excel。

录入过程中会实时校验，不用等到点计算。填错的站名、认不出的时段、重复的编号会立刻标出来，同时告诉你「按现在的数据最多只能填满多少个名额」。

### 高德 API 填在哪

选「高德地图」数据源后，界面上会出现两个输入框：**Key** 和**安全密钥**。都填进去点计算就行。

**Key 的类型。** 在 [高德控制台](https://console.amap.com/dev/key/app) 创建应用后添加 Key，服务平台选 **`Web端(JS API)`**，创建时会同时生成一个安全密钥（`securityJsCode`），两个都要填。

高德还有一种 `Web服务` 类型 Key，面向企业/服务端场景，**个人开发者账号在控制台通常申请不到**（企业认证账号才有这个选项），所以这里没有走那条路。网页版走的是加载高德 JS SDK、用内置的 `AMap.Transfer` 公交换乘插件查询，代码在 `app_ui.js`，源码里用 `▼▼▼ 高德接口接入位 ▼▼▼` 标出来了。

**先点「测试 Key」。** 界面上有个「测试 Key」按钮，一次调用（人民广场 → 徐家汇）就知道 Key 和安全密钥填得对不对，不用等跑完一整批才发现填错了。浏览器控制台会打印原始返回（`[高德原始返回]` 开头），方便核对字段。

**Key 不会被保存**，每次打开页面要重填。录入的数据和通勤缓存会自动存在浏览器本地，刷新不丢。

**调用量控制。** 只查时段能匹配上的站对，示例数据实测 236 次。结果自动缓存；也可以「导出通勤缓存」存成 JSON 分享给同事。项目点站点固定不变，志愿者留存率 60% 到 70%，所以下学期只需为新增站点补算几十次。

**出错处理。** Key 无效、额度耗尽、权限不足这类问题会在第一次调用就中断并说明原因，不会白跑几百次。调用过快（错误码 10004）会自动退避重试。个别站对查不到时退回本地估算，并在结果页标明有几条是估算的。计算过程可以中途取消，已经花掉的调用会保留。

## 二、Python 版

```bash
pip install openpyxl ortools
python3 run.py input_25spring.xlsx     # 求解并输出 Excel
python3 verify.py                       # 独立校验输出
```

打开 `config.py`，只改开头两行：

```python
AMAP_KEY = '你的key'          # 原本是空字符串
AMAP_SECRET = ''              # 留空。只有开了「数字签名」才填私钥
COMMUTE_PROVIDER = 'amap'     # 原本是 'offline'，只填 Key 不改这行是不生效的
```

**注意：Python 版需要的是 `Web服务` 类型 Key，跟网页版的 `Web端(JS API)` Key 不是一回事，不能互用。** 个人开发者账号通常申请不到 `Web服务` 类型（企业认证账号才有），如果你的控制台里没有这个选项，Python 版就用不了真实高德数据，改用 `COMMUTE_PROVIDER = 'offline'` 本地估算，或者直接用网页版。拿不准手上的 Key 是哪种，跑 `python3 check_key.py 你的key` 确认。

接口是公交路径规划 v3：

```
GET https://restapi.amap.com/v3/direction/transit/integrated
    ?key=<AMAP_KEY>&origin=经度,纬度&destination=经度,纬度
    &city=021&cityd=021&strategy=0&extensions=base
```

返回值只取三个字段：`route.transits[0].duration`（在途秒数）、`walking_distance`（步行米数）、`segments` 里的轨道段数减一（换乘次数）。站点经纬度不用你提供，已从地铁拓扑数据里读好。结果缓存到 `commute_cache.json`。

代码在 `commute.py` 的 `AmapProvider.query()`，只有这一处。缓存每 10 次调用落一次盘，中途报错不会白跑；跑的时候会显示进度和预计剩余时间。

输出 `output_分配结果.xlsx`，7 个工作表，含可直接覆盖回填的推荐结果。

## 三、模型

**硬约束**

1. 时段必须完全匹配（沟通记录里的第一优先：「离得很近但时间不对，肯定不行」）
2. 每个志愿者最多带一个班
3. 每个班人数不超过需求数
4. 班级人数不超过需求数

**分层目标**，字典序，逐层求解并锁定上一层的最优值：

1. 最大化「至少有一名志愿者」的班级数，**按上传表格里的教学点 / 班级顺序加权**。表格越靠前的班级权重越高，用来表达反馈中「按教学点顺序依次分配安排」的规则
2. 最大化实际安置人数，即尽量把班配满两人
3. 最小化总通勤代价 = 在途分钟 + 超过单程舒适阈值部分的额外惩罚。在志愿者和教学点班级所需日期/时间匹配的前提下，优先分配单程通勤时间更短的志愿者

分层而不是加权求和，好处是不用调权重，且优先级和机构反馈里的表述严格对应。

**表格顺序权重的含义。** 如果两个班级不能同时覆盖，模型会优先保住上传表格里更靠前的班级；如果第一层目标打平，再比较实际安置人数，最后才比较总通勤代价。

**两个实现，同一套目标。** Python 版用 OR-Tools CP-SAT 逐层求解；网页版用带凸费用弧的最小费用流（班级到汇点的第一条弧费用是 `-(C × 表格顺序权重 + B)`，之后的弧是 `-B`，`C ≫ B ≫ 通勤代价尺度`），数学上等价。

## 四、当前的通勤估算精度

没有高德 Key 时，用内置的上海地铁拓扑（24 条线 416 站，含 15、17、18 号线）建图，站间时间按经纬度距离折算速度，换乘按固定惩罚，Dijkstra 求最短在途时间。

拿常识区间对过，12 组里 9 组落在区间内，其余偏差 2 到 5 分钟：

| 站对 | 本引擎 | 常识区间 |
|---|---|---|
| 人民广场 → 徐家汇 | 12.6 分 | 10 到 13 |
| 人民广场 → 嘉定北 | 63.6 分（换 1 次） | 60 到 75 |
| 永德路 → 殷高东路 | 89.3 分（换 2 次） | 80 到 100 |
| 惠南 → 紫竹高新区 | 113.3 分（换 3 次） | 100 到 135 |

**这个精度够判断结构性缺口，不够当正式排班依据。** 离线估算的换乘惩罚是个固定值，而真实换乘时间在不同站差得很远，这正是沟通记录里提到的那个问题：两个站地理距离近但不同线，实际可能绕一大圈。所以正式使用前请接上高德。

## 五、示例数据的结论

40 人、30 班、60 个名额。每人只带一个班，所以上限是 40 个名额，**结构性缺口 20 个**。

| | |
|---|---|
| 安置志愿者 | 36 / 40 |
| 至少 1 人的班级 | 27 / 30 |
| 配满 2 人的班级 | 9 / 30 |
| 平均单程通勤 | 25.8 分钟 |
| 最长单程通勤 | 61.7 分钟（仅 1 条超 60） |
| 零换乘 | 15 / 36 |

三个班一个人都排不进去，其中 site 7 的周二上午是 0 人可用，属于招募问题而不是排班问题。时段供需表里周日上午缺 5、周六下午缺 2，周五晚上和周日下午则大幅过剩 —— 这张表可以直接拿去指导下一期定向招募，可能比排班表本身更有价值。

## 七、已知限制

- 通勤时间默认是离线估算，见第四节
- 没有服务起止日期字段，稳定性维度完全没有进模型
- 没有老志愿者标记，「回原项目点」的奖励项没有生效（只能靠手工锁定近似替代）
- 没有项目点详细地址，出站后的最后一公里没有计入
- 时段只到「上午 / 下午 / 晚上」的粒度，没有精确钟点

前四项都在《数据需求规格书》里列了。补上之后模型不用改结构，只需在目标函数里加对应项。
